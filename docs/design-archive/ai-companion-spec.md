# Part 1 — 規格書

## Problem Statement

我想在自己的 Windows 電腦上擁有一個「AI 動畫朋友」:我用文字或麥克風跟它說話,它會用我設定好的個性回應、用語音念出來,同時播放符合情緒的說話動畫,並記得我們聊過什麼。我不想買顯卡、不想付費,而且希望我說完話後不必等超過 5 秒它就開口。

## Solution

一個本機運作的桌面應用:後端把使用者訊息與角色人設送給 Gemini(免費額度、Flash-Lite 系列),以串流方式取回回覆;回覆開頭帶一個情緒標籤,之後逐句切開,每句立刻轉成語音(edge-tts)並排隊播放;前端依情緒標籤切換預錄的說話動畫,語音結束後回到待機。所有對話存在本機,角色個性由一份人設檔決定。

## User Stories

1. As a 使用者, I want 用文字輸入跟角色說話, so that 我在安靜的地方也能互動
2. As a 使用者, I want 按住按鍵用麥克風說話, so that 我可以像跟朋友聊天一樣互動
3. As a 使用者, I want 角色在我說完後 5 秒內開口, so that 對話不會有令人焦躁的空窗
4. As a 使用者, I want 角色的第一句話盡快開始播放,不必等整段回覆生成完, so that 感覺是即時的
5. As a 使用者, I want 角色的聲音自然、用中文說話, so that 聽起來像個真實的朋友
6. As a 使用者, I want 角色說話時同步播放說話動畫, so that 它看起來是活的
7. As a 使用者, I want 角色依回覆內容做出微笑、生氣、難過、驚訝等不同表情動畫, so that 情緒傳達更到位
8. As a 使用者, I want 角色沒說話時播放待機動畫(眨眼、微動), so that 畫面不會靜止僵硬
9. As a 使用者, I want 角色等待回覆時顯示思考動畫, so that 我知道它有在處理
10. As a 使用者, I want 角色說完後自動回到待機, so that 畫面狀態合理
11. As a 使用者, I want 用一個文字檔定義角色的名字、個性、說話風格與背景, so that 我能隨時調整人設
12. As a 使用者, I want 修改人設後重新啟動就生效, so that 不必改程式
13. As a 使用者, I want 角色永遠維持人設的口吻, so that 個性前後一致
14. As a 使用者, I want 所有對話歷史保存在我的電腦上, so that 重開軟體後能接著聊
15. As a 使用者, I want 重開後角色仍記得剛才聊的內容, so that 不用重講
16. As a 使用者, I want 能捲動查看過去的對話紀錄, so that 我能回顧
17. As a 使用者, I want 長期聊天後角色仍記得關於我的重要事實, so that 它像真正認識我
18. As a 使用者, I want 過長的歷史被自動摘要, so that 回應速度與額度不被拖垮
19. As a 使用者, I want 免費額度用完或網路不穩時角色仍有合理反應(而非當機), so that 體驗不會中斷
20. As a 使用者, I want 遇到限流時看到友善提示或改以純文字回覆, so that 我知道發生什麼事
21. As a 使用者, I want 角色能被打斷(我開口時它停止說話), so that 對話更自然
22. As a 使用者, I want 角色說的每一句話都能在畫面上看到文字, so that 聽不清時可以閱讀
23. As a 使用者, I want 免費使用、不需要顯卡, so that 我的現有電腦就能跑
24. As a 使用者, I want API 金鑰存在安全的地方而非寫死在程式裡, so that 不會外洩
25. As a 使用者, I want 知道免費層的對話可能被 Google 用於改進產品, so that 我能決定聊什麼
26. As a 使用者, I want 把它包成一個桌面視窗(可選透明背景), so that 它像桌面上的朋友
27. As a 使用者, I want 一鍵啟動 exe, so that 不必開終端機
28. As a 使用者, I want 每次回覆的首音延遲被記錄, so that 我能檢查是否達到即時性目標
29. As a 開發者, I want 語音合成、語音辨識、LLM 都藏在可替換的介面後面, so that 之後能換成離線方案(如 Piper、Kokoro)或更新的模型
30. As a 開發者, I want 情緒集合可設定, so that 我能依製作好的動畫數量調整
31. As a 開發者, I want 核心對話邏輯可在沒有網路、沒有麥克風的情況下自動測試, so that 修改時不會壞掉

## Implementation Decisions

- **模組(深、介面窄):**
  - **對話回合引擎(Turn Engine):** 接收使用者訊息,輸出有順序的事件流:情緒事件、逐句文字事件(其後由語音層補上音訊)、結束事件。內部持有人設、對話歷史,並呼叫 LLM 介面。
  - **LLM 介面:** 一個「給系統提示與訊息、回傳文字串流」的窄介面;預設實作為 Gemini。
  - **語音合成介面:** 一個「給一句文字、回傳音訊」的窄介面;預設實作為 edge-tts,之後可換離線方案。
  - **歷史儲存:** 本機資料庫,保存完整對話;送給 LLM 的只取最近 N 輪加摘要與使用者事實。
  - **角色播放狀態機(Character Player):** 輸入事件流,輸出「目前應播放哪個動畫」(待機、思考、說話加各情緒)。
  - **語音輸入:** 以瀏覽器內建語音辨識為預設,按鍵說話;之後可換 faster-whisper。
  - **桌面外殼:** 用網頁技術包成桌面視窗與 exe。
- **平台(第 8 張票時修正):** 後端 Python、前端網頁技術。預設用 Edge 的應用程式視窗承載,而不是 Tauri 或 Electron,因為瀏覽器內建語音辨識在 Electron 內無法使用、在 WebView2 也不確定可用;另提供 pywebview 的桌寵模式(無邊框、置頂、可拖曳)作為選用;pywebview 在 Windows 不支援透明視窗,且語音輸入在該模式下可能不可用。
- **模型:** 預設 `gemini-3.5-flash-lite`(免費額度約每日 500 次,遠高於 3.8 Flash 的約 20 次);模型名稱可設定。thinking 設 low;不使用已棄用的 temperature、top_p、top_k,語氣完全由人設控制。不使用 Antigravity 託管 agent(為長任務設計,不適合即時聊天)。
- **情緒傳遞(與先前討論的差異):** 為了能逐句串流,情緒改為「回覆開頭的一個標籤」,而非整段 JSON。標籤不在允許集合內或缺漏時,退回 neutral。預設 5 種:neutral、happy、angry、sad、surprised(可設定)。
- **逐句串流:** 遇到句尾標點(。!?!?…)或換行即切句並立刻送出;串流結束時把剩餘文字當最後一句。
- **人設:** 純文字檔,啟動時讀入;系統提示 = 人設 + 情緒標籤規則 + 「第一句請簡短」。
- **歷史:** 送給 LLM 的歷史保留含情緒標籤的原始回覆,讓模型持續遵守格式;畫面顯示時另行去除標籤。
- **延遲預算:** 目標首音 ≤ 約 3 秒,硬性上限 5 秒。
- **額度感知:** 遇 429 或逾時要降級(純文字提示、稍後重試),不得當機。
- **金鑰:** 存環境變數或 Windows 憑證管理員。

## Testing Decisions

- **好測試的標準:** 只測外部可觀察行為,不測實作細節;測試名稱讀起來像規格;重構內部時測試不應壞。
- **已確認的接縫(只在這兩處寫測試):**
  1. **對話回合引擎(後端):** 輸入訊息與人設,觀察事件流與送往 LLM 的內容,以及歷史是否被保存。Gemini 與 edge-tts 只在最外緣以替身取代。
  2. **角色播放狀態機(前端):** 輸入事件流,觀察應播放的動畫狀態。
- **不寫自動測試:** 影片實際畫面、麥克風、桌面打包 — 人工驗收。
- **即時 Gemini 呼叫**只作為手動冒煙測試,不進自動化。
- **Prior art:** 全新專案,無既有測試。
- **TDD 規則:** 紅先於綠;一次一個切片(一個接縫、一個測試、一個最小實作);不預先寫未來測試。

## Out of Scope

- 3D 角色、Live2D、VRM 與音素級口型同步
- 離線語音合成(Piper、Kokoro)— 僅預留介面
- Gemini Live API(原生語音對語音)
- 手機版、多角色切換、雲端同步
- 付費層與多使用者

## Further Notes

- 模型名稱與免費額度依 2026 年 9 月的文件與第三方整理,各來源數字略有出入,請以 AI Studio 帳號顯示為準。
- edge-tts 並非本機運算,而是呼叫 Microsoft 線上服務(非官方),可能失效,因此必須藏在介面後面。
- 免費層內容可能被 Google 用於改進產品,不適合放敏感資料。
- 長期記憶:歷史超過 20 輪後,背景每約 10 輪整理一次「摘要加使用者事實」,約多 1 次請求;失敗時不影響對話並於之後重試。
- 目前的限制:程式為單一使用者、單一引擎;同時開多個分頁或快速連續送出,可能互相干擾。

# Part 3 — 規格書:語音直送模型與逐句情緒

> 狀態:規格已透過 grilling 與使用者對齊(Q1–Q7 皆已回答)。票券拆分已由使用者核准,見 Part 4。
> 來源:另一專案的未實作 spec,只搬「行為」兩項;外加使用者實測回報的 bug(同一則回覆出現兩個情緒標籤,第二個被當成台詞念出來)。
> 沿用既有的兩個測試接縫,不新增。
> **本部分取代 Part 1 中「情緒標籤只在回覆開頭出現一次」的決定。**

## Problem Statement

1. **語音要先被辨識成文字。** 現在按住說話時,聲音先交給瀏覽器內建的語音辨識,轉成文字後才送給模型。這多了一層依賴(要 Edge/Chrome、要連網、桌寵模式可能不能用),辨識錯字也會直接污染整段對話。
2. **一則回覆只有一個情緒。** 目前情緒標籤只出現在整段回覆的開頭,回覆再長,動畫也只有一種表情。
3. **標籤會被念出來(實測 bug)。** 模型會在回覆中間再插入一個標籤,例如「[thinking]我想想看要怎麼解決這個問題[neutral]算了,不想了」。第一個標籤被正確處理,第二個因為前面沒有句號,連同前面的文字黏成一句,並且把「[neutral]」當台詞唸了出來。已在現有引擎上重現;即使前面有句號,第二個標籤同樣會被唸出來。

## Solution

按住說話時,瀏覽器錄下原始聲音,直接送給 `gemini-3.5-flash-lite`。模型先輸出你說的話的逐字稿,再回覆;逐字稿只用於顯示與存歷史,不會被念出來。

模型的每一句話開頭都帶一個情緒標籤。引擎在串流中逐句解析,標籤一律不進入台詞(無論它出現在哪裡、格式多怪),每句話的動畫在那一句的聲音開始播放的那一刻切換。

## User Stories

**語音直送模型**

1. 作為使用者,我想要按住按鍵說話、放開後聲音直接送給模型,以便不再依賴獨立的語音辨識
2. 作為使用者,我想要錄音時看到「錄音中」和已錄秒數,以便知道系統有在收音
3. 作為使用者,我想要太短的錄音(約 0.5 秒以下)不被送出並得到提示,以便誤觸不會產生一次無意義的對話
4. 作為使用者,我想要錄音有長度上限(60 秒),以便不小心錄太久不會讓請求失敗
5. 作為使用者,我想要在對話中看到我說的話被轉成的文字,以便確認角色有沒有聽錯
6. 作為使用者,我想要模型聽不清楚時角色用人設的口吻反問,而且這個回合仍然被記錄,以便對話自然接續
7. 作為使用者,我想要歷史只保存文字、不保存聲音,以便資料庫不膨脹,之後的回合也不用重送音訊
8. 作為使用者,我想要在角色說話或思考時再次按住說話就能打斷它,以便像真人對話(既有行為,需保留)
9. 作為使用者,我想要文字輸入照常可用,以便在安靜的地方互動
10. 作為使用者,我想要音訊被拒收或網路失敗時得到友善提示與重試,而且重試用的是同一段錄音,以便不用重講一次
11. 作為使用者,我想要清楚知道我的原始語音會被送給 Google Gemini(免費層可能被用於改進產品),以便決定要不要語音聊私事
12. 作為開發者,我想要一支 smoke 腳本,用真實錄音檔驗證 Gemini 是否接受這種格式、能不能聽懂中文,以便接前端之前先確認
13. 作為開發者,我想要音訊輸入藏在 LLM 介面後面並可用替身測試,以便沒有網路也能自動驗證

**逐句情緒**

14. 作為使用者,我想要每一句話有自己的情緒,以便先驚訝後開心時動畫能逐句切換
15. 作為使用者,我想要每句的動畫在那句聲音開始播放的那一刻才切換,以便嘴型、表情和聲音一致,而不是文字一到就換
16. 作為使用者,我想要情緒標籤永遠不被唸出來、也不出現在文字裡,即使模型把它插在句中、前面沒有標點、用全形括號、大小寫不一或帶空白,以便聽起來自然
17. 作為使用者,我想要模型漏標某一句時沿用上一句的情緒,以便畫面不亂跳
18. 作為使用者,我想要模型寫出清單以外的標籤(例如 thinking)時有合理預設,以便不會找不到動畫或出錯
19. 作為使用者,我想要標籤剛好被切在串流片段的交界時也能正確處理,以便偶發的切法不會壞掉
20. 作為使用者,我想要舊的對話紀錄(只有開頭標籤,或含舊 bug 遺留的句中標籤)顯示時也是乾淨的,以便回顧歷史不會看到雜訊
21. 作為使用者,我想要每則回覆旁看到它的情緒序列(例如 happy → sad),以便確認和除錯
22. 作為使用者,我想要結尾孤立的標籤或連續的標籤不產生奇怪的空句子,以便聲音與畫面乾淨
23. 作為使用者,我想要第一句話仍然盡快開始播放,不因為情緒解析而變慢,以便維持首音 5 秒內的目標
24. 作為使用者,我想要長期記憶的摘要與事實抽取用的也是不含標籤的文字,以便記憶內容不被雜訊污染
25. 作為開發者,我想要情緒清單仍然可以設定,以便依製作好的動畫數量調整
26. 作為開發者,我想要「清單外標籤如何處理」的規則集中在一處,以便實測後容易調整

## Implementation Decisions

**範圍**
- 只搬兩項行為:語音直送模型、逐句情緒;另含標籤外洩 bug 的修正。
- 不搬:Electron、TypeScript、Vitest 技術棧;情緒名稱 `calm`(維持 `neutral`,動畫檔名不變);JSON 歷史檔;改用 3.1 模型(維持 `gemini-3.5-flash-lite`);「下一句提前合成」預抓;6 支素材對照。

**音訊輸入**
- 錄音由瀏覽器錄音功能(MediaRecorder)產生,以原始格式(webm)直接送出,不做轉檔;音訊以 `audio/webm` 標示。
- 維持現有的 GenerateContent 串流呼叫,不遷移到 Interactions API。
- **驗證關卡(人工):** 在接前端之前,先由使用者執行 smoke 腳本,確認 Gemini 接受該格式並能聽懂中文。若被拒收,改為由瀏覽器端先轉成 WAV,其餘設計不變,不需重開規格。
- 新增一個接收原始位元組(以 Content-Type 標示格式)的音訊對話端點;文字對話端點不變。
- 對話回合引擎的輸入可以是文字或音訊;LLM 介面的訊息內容可以包含音訊;歷史一律只存文字。
- 音訊回合會在使用者輪附一段文字指示,要求模型**先**輸出以 `<heard>…</heard>` 包起來的逐字稿,再輸出情緒標籤與回覆。引擎把它解析成新的「逐字稿事件」,逐字稿不會被念出、也不算回覆的一部分。
- `<heard>` 缺漏時,使用者訊息存成「(語音訊息)」,回覆照常處理。模型聽不清楚時,逐字稿應為「(聽不清楚)」,該回合照常存入歷史,角色以人設口吻反問。
- 失敗與重試維持既有規則:失敗的回合不存;重試沿用同一段錄音(只保留在記憶體,不寫入磁碟)。
- 前端:**完全移除**瀏覽器語音辨識,按住說話(按鈕與 F2)只走錄音;錄音中顯示計時取代即時字幕;錄音短於約 0.5 秒不送出、回到待機並提示;上限 60 秒;使用者氣泡在收到逐字稿事件時才顯示。
- 隱私:原始語音現在直接送給 Google Gemini。README 與 SETUP 中關於「麥克風音訊送給瀏覽器辨識服務」的說明需同步改為新的資料流向。

**逐句情緒**
- 提示詞規則(由程式自動附加,使用者不用維護):每一句開頭必須有一個情緒標籤;只能用清單內的種類;每句以標點結尾;不要在句中插標籤。此規則的實際遵從度需靠實測,程式端的防線不依賴它。
- **什麼算標籤:** 任何半形 `[…]` 或全形 `【…】`,內容 1 到 16 個字元、不含括號、前後空白容忍、不分大小寫。內容超過 16 字元的不算標籤,原樣保留為文字。
- **標籤的情緒:**
  - 在清單內 → 該情緒。
  - 不在清單內、且後方有說話 → happy。
  - 不在清單內、且後方沒說話 → neutral。
  - 「後方」指從該標籤結束,到下一個標籤或回覆結束之間的文字;去除空白後仍有內容,就算有說話。
  - 沒有標籤的句子沿用上一個情緒;整則回覆第一句沒有標籤 → neutral。
- **串流處理:**
  - 遇到新標籤,前面尚未收尾的文字先當一句送出,情緒用前一個。
  - 標籤可能被切在兩個串流片段之間,尾端疑似標籤的殘片要暫扣到能判斷為止,但已完整的句子不得因此被延遲。
  - 結尾孤立的標籤丟棄,不產生句子;連續標籤以最後一個為準。
  - 標籤在切句時就由同一個解析器剝除,所以送往語音合成與畫面的每一句文字結構上不含標籤(實作上不另設清洗步驟;歷史顯示與長期記憶摘要也用同一個解析器)。
- **事件契約(行為規格變更):** 逐句文字事件與音訊事件各自帶有情緒;移除原本「整則回覆一個」的獨立情緒事件;新增逐字稿事件。既有測試中編碼了舊契約的部分,將依新契約改寫,不視為「被弄壞」。
- **角色播放狀態機:** 音訊開始播放的事件要指出是第幾個片段,狀態機依該片段的情緒切換動畫。句與句之間的空檔仍維持說話狀態;打斷、聆聽、思考短音的語意不變;未知情緒仍退回備援情緒。
- **歷史:** 儲存含標籤的原始回覆(維持,讓模型持續遵守格式);顯示與長期記憶摘要一律使用同一套解析,得到每則回覆的逐句情緒序列與不含標籤的文字。舊資料自動適用,不需遷移。
- **已知副作用(使用者選擇「任何括號都算標籤」的後果):** 一般文字裡的方括號(例如 `arr[0]`)會被當成標籤吃掉,並以 happy 處理;`[thinking]` 後面接著話時,會套用 happy 動畫(原本是 neutral)。規則集中在一處,實測後若不合意,可單點調整。

## Testing Decisions

- **好測試的標準(沿用):** 只驗證外部可觀察行為,不驗證實作細節;測試名稱讀起來像規格;內部重構時測試不應壞。紅先於綠,一次一個切片。
- **測試接縫(沿用兩個既有接縫,不新增):**
  1. **對話回合引擎:** 輸入文字或音訊與人設,觀察事件流、送往 LLM 的內容、歷史保存與顯示。Gemini 與 edge-tts 只在最外緣以替身取代。
  2. **角色播放狀態機:** 輸入事件流,觀察應播放的動畫狀態。
- **對話回合引擎要驗證的行為:**
  - 使用者回報的案例:兩個標籤、無句號 → 台詞不含標籤,拆成兩句,各自情緒正確。
  - 第二個標籤前有句號 → 同樣乾淨。
  - 標籤被切在串流片段交界(含全形括號、大小寫、空白) → 仍被辨識並剝除。
  - 已完整的句子在後面片段到達前就送出,不被標籤解析延遲。
  - 沿用上一句情緒;第一句無標籤 → neutral。
  - 清單外標籤且後方有說話 → happy;結尾孤立標籤不產生句子;連續標籤取最後一個。
  - 內容超過 16 字元的括號保留為文字。
  - 音訊輸入:LLM 收到音訊;逐字稿事件在回覆之前;歷史存的是逐字稿文字;`<heard>` 缺漏 → 「(語音訊息)」;聽不清楚 → 照常存歷史;失敗不存、重試不重複。
  - 歷史顯示與摘要:回傳逐句情緒與乾淨文字;舊格式紀錄(只有開頭標籤、含遺留句中標籤)也正確。
- **角色播放狀態機要驗證的行為:** 依片段情緒切換,切換點是該片段開始播放;句間空檔維持說話;未知情緒退回備援;打斷後舊片段的殘餘事件不影響;聆聽與思考短音行為不變。
- **不寫自動測試(人工驗收):** 錄音與錄音前端、真實 Gemini 是否接受 webm 與中文辨識品質、畫面與動畫實際切換、桌寵模式的麥克風。
- **Prior art:** 既有兩套測試(後端 23 個、前端 17 個)的風格與替身(LLM、TTS、時鐘、背景執行)沿用。

## Out of Scope

- 改用 Electron / TypeScript / Vitest,或任何搬遷語言與框架的動作
- 情緒名稱改為 `calm`、增減情緒種類

- 離線語音辨識(faster-whisper 等)

# Part 5 — 規格書:語音開頭裁切修正、持續對話、口型同步

> 狀態:規格已透過 grilling 與使用者對齊。**票券拆分待使用者確認,見 Part 6。**
> 來源:①使用者實測回報「說話前 3-5 個字沒念出來」;②使用者提出兩個新目標,透過 `/grill-me` 對齊(Q1–Q11 皆已回答,含追問)。
> **流程上的偏離(使用者明確同意):** 第 11 張票的 smoke 關卡(真實 Gemini 是否接受 `audio/webm`)尚未執行,使用者選擇先實作、之後補測。細節與圍堵方式見「音訊格式未驗證的圍堵」一節。

## Problem Statement

1. **語音開頭被裁切(bug):** 使用者實測時,角色說話的前 3-5 個字沒有被念出來,畫面上的文字沒有少。三個範例都發生,不是偶發。
2. **還是要按鍵才能說話:** 目前語音輸入(無論是舊的瀏覽器辨識或第 11 張票的音訊直送)都得按住 F2 或按鈕。使用者想要像跟真人講話一樣,不用一直按,講完一句系統自己知道该送出了。
3. **角色講話時嘴巴不會動:** 目前只有整段影片的既定動畫,嘴巴開合跟聲音無關。使用者想要嘴型至少有基本的對應。

## Solution

**開頭裁切:** 懷疑是瀏覽器播放沒有正確時長標頭的 MP3 Blob 時,為了推算時長而往前跳過一小段所致(而非 `edge-tts` 服務端裁切)。修法在前端播放邏輯,不改變送給 TTS 的文字內容。

**持續對話:** 新增一個可切換的「持續聆聽」模式,與現有的按鍵說話並存。開啟後,瀏覽器用簡單的音量門檻自動偵測你開始說話、安靜多久算講完,自動把整段錄音送去 `/chat/audio`(第 11 張票已完成的端點),不需要按鍵。角色說話時麥克風照常開著,靠瀏覽器內建的回音消除擋掉喇叭聲;若偵測到角色反覆被自己的殘留聲音打斷,自動退回「角色說話時麥克風靜音」並提示使用者,下次重新開啟持續聆聽時再給一次機會。F2 在持續模式下改為「立刻強制打斷」的手動保險。

**口型同步:** `edge-tts` 的串流其實會回傳逐字的時間戳(`WordBoundary`,含每個字詞的 offset/duration),目前的轉接器把它丟棄。改為擷取這筆時間資訊,前端依照字詞的時間範圍切換「嘴巴開/閉」,疊加在既有影片上方固定的位置。使用者自行提供疊加素材,不做佔位圖;有最短停留時間避免閃爍。

## User Stories

**語音開頭裁切**

1. 作為使用者,我想要角色說的每一句話從第一個字就聽得到,以便不會漏掉內容或誤以為它卡住
2. 作為開發者,我想要這個修正不影響歷史、記憶或送給 TTS 的文字,以便跟既有行為維持一致

**持續對話**

3. 作為使用者,我想要開啟「持續聆聽」後,直接開口說話就會被送出,不用按鍵或按鈕,以便像跟真人聊天一樣自然
4. 作為使用者,我想要在持續聆聽和按鍵說話之間切換,以便吵雜環境或想安靜打字時退回按鍵模式
5. 作為使用者,我想要清楚看到目前是不是在持續聆聽,以便知道麥克風是不是開著
6. 作為使用者,我想要角色說話時我開口就能打斷它,不需要按鍵,以便對話跟真人一樣自然
7. 作為使用者,我想要即使回音消除沒能完全擋住角色自己的聲音,系統也不會一直自問自答下去,以便體驗不會失控
8. 作為使用者,我想要在持續聆聽模式被系統自動關閉時得到明確提示,並且下次重新開啟時再給一次機會,以便知道發生了什麼事、且不被永久卡住
9. 作為使用者,我想要在持續聆聽模式下,F2 仍然可以立刻強制打斷角色,以便在自動偵測失靈時有手動的保險
10. 作為使用者,我想要太短或聽不清楚的聲音不會被誤送,以便安靜的環境噪音不會一直觸發對話、浪費額度
11. 作為使用者,我想要連續好幾次都聽不清楚時,系統提示我要不要切回按鍵模式,以便吵雜環境下不會一直無謂地消耗免費額度
12. 作為開發者,我想要語音起訖的判斷邏輯是純函式,可以離線自動測試,以便修改時不容易壞掉
13. 作為使用者,我想要按鍵說話功能完全不受影響,以便舊的操作方式仍然堪用

**口型同步**

14. 作為使用者,我想要角色說話時嘴巴會跟著開合,而不是整段影片嘴型固定,以便看起來更生動
15. 作為使用者,我想要嘴巴開合大致跟著字詞的節奏走,而不是完全跟聲音無關的固定動畫,以便更貼近真的在說話
16. 作為使用者,我想要嘴型不要因為字詞切太快而一直閃爍抖動,以便看起來自然
17. 作為使用者,我想要自己提供嘴型素材,以便畫面風格由我掌控
18. 作為使用者,我想要沒有放嘴型素材時,畫面维持現有的樣子,以便這個功能是漸進加上去的,不會讓沒素材的人畫面壞掉
19. 作為開發者,我想要中文的字詞時間戳粒度(以字為單位還是以詞為單位)有辦法在使用者的機器上被實際看到,以便日後調整防閃爍的數值

## Implementation Decisions

### 開頭裁切修正

- **懷疑原因:** 瀏覽器對沒有正確時長標頭的 MP3 Blob 做時長推算時,可能導致播放起點往後跳一小段。**這只是假設,沒有在真實環境驗證過**,使用者實測後才能確認。
- **修法(前端,`static/index.html`):** 建立 `<audio>` 後,明確等待中繼資料就緒、並在播放前把 `currentTime` 校正回 0,而不是建立後立刻呼叫 `play()`。
- **範圍:** 只改播放邏輯,不改 `EdgeTTS.synthesize()`、不改送進 TTS 的文字、不改任何送給 LLM 或存進歷史的內容。
- **若假設錯誤:** 這個修正不會讓情況變差(最壞情況是沒有效果),真正的原因需要使用者提供的實機資訊(例如：問題是否每句都發生、是否跟句子長短有關)才能進一步排查。

### 音訊格式未驗證的圍堵

- 第 11 張票的 smoke 關卡(`smoke_audio.py`)尚未執行。使用者選擇先實作第 15、16 張票,之後再補跑。
- **圍堵方式:** `GeminiLLM` 若因音訊格式被拒收而收到錯誤,經由既有的 `to_llm_error` 轉換,歸類為現有錯誤種類之一並顯示友善提示,不會讓伺服器或頁面崩潰(既有機制,本次不需要新增分類)。
- **假設落空時的退路:** 依 Part 3 已定案的計畫,改為瀏覽器端先轉成 WAV 再送出,不影響 VAD、回音消除、嘴型同步的設計。
- 這個關卡在票券的驗收項目中維持存在,標記為「實作可先行,正式視為可用前必須勾選」。

### 持續對話

- **語音起訖偵測(VAD):** 純前端邏輯,讀取麥克風音量,設定「安靜多久算講完」與「太短就忽略」兩個門檻,皆可用環境變數調整(比照既有 `COMPANION_*` 慣例):
  - `COMPANION_VAD_SILENCE_MS`(預設 700):安靜超過這個時間視為一句話講完。
  - `COMPANION_VAD_MIN_MS`(預設 500):錄到的聲音短於這個時間,直接忽略、不送出,跟按鍵模式的既有門檻一致。
  - 不引入外部語音偵測套件或模型,維持純 JS、輕量的既有原則。
- **模式切換:** 畫面新增一個「持續聆聽:開/關」的切換控制;切到開才會請求麥克風權限(不預先或自動要求),符合既有的權限提示行為。切到關時,回到現有的按鍵說話流程,完全不受影響。
- **偵測到的一句話怎麼送出:** 沿用第 11 張票已完成的 `/chat/audio`;偵測到的一段錄音等同一次按鍵說話放開後的行為。
- **回音與插話:**
  - 角色說話時麥克風**照常開著**,錄音端加上 `echoCancellation: true`,依賴瀏覽器內建的回音消除濾掉喇叭聲。
  - TTS 播放維持用 `<audio>` 元素(不透過 Web Audio API 混音),讓瀏覽器的回音消除拿得到官方播放路徑當參照訊號;口型同步(下方)不得破壞這一點。
  - **自動退回機制:** 若連續判定使用者「插話」但辨識結果是空的或「(聽不清楚)」,達到一個次數門檻(建議 3 次),自動把持續聆聽模式切換為「角色說話時麥克風靜音」的保守設定,並跳出明確提示告訴使用者發生了什麼、以及可以怎麼做。下一次重新開啟持續聆聽時,先從「麥克風照常開著」重新開始,不永久卡在保守設定。
  - F2 在持續模式下的定位改變:不再是「按住才錄音」,而是「立刻強制打斷角色」的手動保險,不論自動偵測與回音消除是否正常運作都能用。
- **誤觸發與額度保護:**
  - 沿用 `COMPANION_VAD_MIN_MS` 過濾掉短促雜音。
  - 連續 3 次逐字稿是「(聽不清楚)」或空白,自動暫停持續聆聽,跳出提示詢問是否要切回按鍵模式。
- **測試接縫(新增,經使用者同意):** VAD 的門檻判斷邏輯(給一串音量讀數與兩個門檻,輸出「該不該送出」「有沒有講完」)寫成不碰瀏覽器 API 的純函式,獨立測試檔,原則與既有的 `CharacterPlayer` 接縫相同(紅先於綠、只測外部可觀察行為)。這是本次唯一在原本兩個接縫之外新增的測試對象。

### 口型同步

- **時間資料來源:** `edge_tts.Communicate(...).stream()` 的訊息含 `type: "WordBoundary"`,附 `offset`、`duration`(100 奈秒為單位)。`EdgeTTS.synthesize()` 目前只收集 `type == "audio"` 的區塊,需改為同時收集 `WordBoundary`,回傳音訊位元組與時間戳清單兩者。
- **粒度未知:** 中文的 `WordBoundary` 是以字還是以詞為單位切,沒有在真實環境驗證過(沙盒連不到微軟服務)。`smoke_tts.py` 需改為額外印出取得的時間戳,讓使用者下次執行時能看到實際粒度。
- **疊加方式:** 前端依照目前播放位置(`audio.currentTime`)比對時間戳清單,落在某個字詞的區間內時疊加「嘴巴張開」素材,區間之外顯示「嘴巴閉合」(即不疊加,退回底圖原本的嘴型)。
- **防閃爍:** 開合狀態切換後,至少維持 `COMPANION_MOUTH_MIN_MS`(預設 80)才能再變化,避免字詞間隔過短時視覺閃爍。可調。
- **素材規格:** 使用者提供**一個共用**的嘴型素材(不分情緒),放在 `clips\mouth-open.webm` 或 `.png`;疊加的位置與大小由一個小設定檔指定(座標與寬高,相對於畫面的百分比,使用者自行量測填入)。**沒有放這個檔案時,完全不疊加,畫面維持現有行為**,不影響沒有素材的使用者。
- **測試接縫:** 疊加時間表的計算(給一串 `{offset, duration}` 與最短停留時間,輸出開合區間)是純函式,比照 VAD 的邏輯一併寫自動測試。實際的疊加繪製(DOM/影片合成)屬於 `index.html` 膠水碼,不自動測試。
- **提示詞:** 不需要修改,情緒標籤的規則與口型同步無關,兩者互相獨立。

## Testing Decisions

- **沿用原則:** 只驗證外部可觀察行為,不測實作細節;測試名稱讀起來像規格;紅先於綠,一次一個切片。
- **接縫(本次共三個,較先前兩個多一個,經使用者於 Q4 同意):**
  1. **對話回合引擎** `TurnEngine`(後端,既有):本次不涉及事件契約變動,`EdgeTTS` 改動屬於最外緣轉接器,不在此接縫內測試。
  2. **角色播放狀態機** `CharacterPlayer`(前端,既有):驗證嘴型疊加的開合狀態切換(給定目前播放時間與時間表,輸出目前該不該疊加)。
  3. **語音起訖判斷**(前端,新增):純函式,給音量讀數序列與門檻,輸出「送出/忽略/尚未講完」的判斷。
- **不寫自動測試(人工驗收):**
  - 開頭裁切修正是否真的解決(需要真實瀏覽器與真實 TTS)。
  - 真實麥克風下的持續聆聽體驗、回音消除實際效果、自動退回機制是否被正確觸發。
  - 中文 `WordBoundary` 的實際粒度與嘴型疊加的實際觀感。
  - 音訊格式是否被 Gemini 接受(`smoke_audio.py`,仍是第 11 張票的關卡,只是不再阻擋開工)。
- **Prior art:** 沿用既有兩個接縫的風格;新增的第三個接縫刻意維持同樣的簡潔標準,不引入測試框架以外的套件。

## Out of Scope

- 音素級口型(對應到嘴型形狀本身,而非單純開合);要做到這個等級需要 Live2D 或 VRM 這類分層角色,推翻「預錄影片」的核心設計,不在本次範圍(維持 Part 1 原本的 Out of Scope 決定)。

## 18 — 持續聆聽與音訊直送的實測 bug 修正(第二輪,使用者實測回報)

### Parent
規格書 Part 5(2026-09-26 追加)

### What to build
使用者在持續聆聽模式下實測,回報五個現象,合併在本票一次處理。前四個共用同一個根本原因——`<heard>` 判斷一旦判定「這回合沒有逐字稿」,原本會把之後收到的所有原始文字整段直接當成台詞送出,不再檢查裡面是不是還藏著一個真正的 `<heard>…</heard>`;這樣的回合一旦被存進歷史,模型看到自己過去講過這種格式,之後更容易照樣重複,問題因此在某次之後就持續出現、越來越常見。第三、四個現象另外有一個獨立成因:引擎是單一實例、單一使用者,但打斷(barge-in)是「前端立刻中止舊的 fetch、馬上送出新的」,伺服器端的舊回合不會因此真的停止,兩個回合會共用同一份計時/TTS 失敗旗標,舊回合還可能在被放棄之後才存進歷史,污染之後的對話記憶,也讓原本正常的打斷被前端誤算成一次「聽不清楚」。第五個現象是第 17 張票「根因不明」的後續:edge-tts 對完全沒有內容可念的句子(例如切分後只剩一個單獨的刪節號)不是回傳空位元組,而是直接丟出 `NoAudioReceived` 例外,原本的例外處理把這當成「整個語音服務壞了」,關掉了這一輪剩下所有句子的語音——這才是真正吃掉「才不是想跟你烤肉呢」這句聲音的原因,不是那句話本身有問題。

### Acceptance criteria
- [x] 判斷「沒有 `<heard>`」之後,若原始文字後續仍出現 `<heard>…</heard>`,整段(含標籤)一律剝除,不顯示、不送去合成語音(`companion/engine.py` 的 `strip_stray_heard`)
- [x] 送給模型的歷史內容(`send()` 組出的 `past` messages)一律先做同樣的剝除,即使是這次修正之前就已經存進 `history.db` 的舊資料,也不會再被當成格式範例回放給模型
- [x] `TurnEngine` 不再用實例屬性保存單一回合的計時與 TTS 失敗旗標(改成 `_Turn` 這個每次呼叫各自獨立的物件);兩個回合同時在跑也不會互相干擾
- [x] 呼叫 `send()` 即視為「這是最新的一輪」(呼叫當下就生效,不必等第一次被讀取);更舊、還沒跑完的一輪一旦發現自己被取代,安靜結束,不會把回合存進歷史、也不會動到新回合的狀態
